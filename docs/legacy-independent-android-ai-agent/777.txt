Independent Android AI Agent — MVP Architecture v0.1

Переходим к следующему фундаментальному документу. Здесь мы впервые определим не только принципы, но и конкретные архитектурные модули, их обязанности и взаимодействие.

Главная задача — создать минимальную работающую версию автономного Android-агента, не загнав будущий проект в архитектурный тупик.

Моё предложение: строим небольшое, но настоящее ядро агента, а не демонстрационный чат, который потом придётся переписывать.

Independent Android AI Agent

MVP Architecture v0.1 · Архитектурный проект

Автономность, сменяемые модели, безопасное выполнение, проверяемый результат и независимость от облака.

1. Что именно строим в MVP

Первая версия должна уметь принимать цель на естественном языке, определять подходящий способ её достижения, выполнять доступные действия на Android и проверять результат.

Например, пользователь говорит:

«Создай напоминание купить продукты сегодня в 18:00».

Агент должен не просто сгенерировать текст с обещанием, а пройти полный цикл:

Понять цель и извлечь дату, время и содержание.

Определить, какие возможности устройства подходят для задачи.

Проверить разрешения и необходимость подтверждения.

Выполнить действие доступным способом.

Проверить, что напоминание действительно создано.

Сообщить пользователю проверенный результат.

Если необходимого доступа нет, агент должен объяснить ограничение и предложить альтернативу.

2. Общая архитектура

Interaction Layer

Аватар · Голос · Текст · Рабочая область · STOP

Agent Core

Управление жизненным циклом задачи

Goal Model

Понимание цели и критериев успеха

Planner

Разработка и пересмотр плана

Strategy Engine

Сравнение доступных способов

Safety & Policy

Риски, разрешения и подтверждения

Execution Engine

Управляемое выполнение · Отмена · Контроль состояния

Capability System

Доступные действия и их контракты

Verification

Проверка фактического результата

Поддерживающие сервисы: Model Adapter · Local State · Experience Store · Audit Log

Это логическая схема, а не требование создать отдельный Android-модуль для каждого блока. На старте некоторые компоненты могут находиться в одном модуле, сохраняя чёткие границы ответственности.

3. Ответственность модулей
3.1. Agent Core — управляющее ядро

Это главный координатор системы.

Он отвечает за жизненный цикл задачи:

RECEIVE → UNDERSTAND → PLAN → AUTHORIZE → EXECUTE → VERIFY → COMPLETE

Если задача не завершилась успешно, ядро решает, следует ли повторить проверку, построить альтернативный план, запросить пользователя или остановиться.

Agent Core не должен быть привязан к конкретной LLM, экрану или механизму автоматизации Android.

3.2. Goal Model — модель цели

Преобразует пользовательский запрос в структурированное представление.

Пример:

{
  "goal_type": "create_reminder",
  "desired_outcome": {
    "title": "Купить продукты",
    "datetime": "2026-10-07T18:00:00"
  },
  "success_criteria": [
    "reminder_exists",
    "datetime_matches"
  ],
  "constraints": [],
  "requires_clarification": false
}

Это иллюстрация контракта, не готовая реализация. Формат времени и часовой пояс в настоящем контракте должны быть определены явно.

Модель цели должна сохранять:

желаемый результат;

ограничения пользователя;

критерии успеха;

неопределённости;

допустимые изменения плана.

Важно: Goal Model не должна подменять намерение пользователя догадками модели. Если неоднозначность влияет на результат или безопасность, агент задаёт уточняющий вопрос.

3.3. Planner — планировщик

Строит последовательность шагов для достижения цели.

Например:

Goal: Создать напоминание
       ↓
1. Определить подходящий механизм
       ↓
2. Проверить доступ и ограничения
       ↓
3. Создать напоминание
       ↓
4. Проверить его наличие
       ↓
5. Сообщить результат

Planner определяет, что нужно сделать. Он не получает безусловного права исполнять собственный план.

3.4. Strategy Engine — движок стратегий

Сравнивает альтернативные способы выполнения.

Например, для создания напоминания могут рассматриваться:

доступная системная функция Android;

официальный интерфейс приложения;

другое установленное приложение с подходящими возможностями;

контролируемая UI-автоматизация, если она допустима и доступна;

предложение пользователю выполнить недоступный шаг самостоятельно.

Каждая стратегия оценивается по доступности, вероятности успеха, риску, стоимости, требуемым разрешениям и возможности проверки.

На MVP достаточно нескольких стратегий и понятного механизма выбора. Не требуется сразу создавать универсальный поиск по всем приложениям Android.

3.5. Safety & Policy — безопасность

Это отдельный обязательный слой, который проверяет план до выполнения и контролирует действия во время исполнения.

Предлагаемые классы действий:

Класс

	

Поведение




Низкий риск

	

Выполнение в рамках выданных разрешений




Требуется подтверждение

	

Запрос согласия перед соответствующим действием




Высокий риск

	

Усиленная проверка и явное подтверждение, если действие вообще допустимо




Запрещено

	

Отказ от выполнения

Конкретные категории и правила нужно будет закрепить в отдельной Safety Policy.

Важное правило: подтверждение не может предоставлять агенту системные разрешения, которых Android ему не выдал, и не может отменять запреты политики.

3.6. Execution Engine — движок выполнения

Исполняет разрешённый план через доступные capabilities.

Он должен поддерживать:

ограничение времени выполнения;

отмену;

контроль промежуточных состояний;

обработку ошибок;

безопасное прекращение последовательности;

передачу результата в Verification.

Особенно важно разделять отмену и откат. Если агент уже отправил сообщение или совершил другое необратимое действие, STOP не может гарантировать отмену произошедшего. Он должен прекращать последующие действия и по возможности безопасно останавливать текущую операцию.

3.7. Capability System — система возможностей

Каждая доступная операция описывается единым контрактом.

Capability
 ├── id
 ├── description
 ├── input_schema
 ├── output_schema
 ├── permissions
 ├── risk_level
 ├── execution_adapter
 ├── availability_check
 └── verification_strategy

Это позволит подключать новые способы выполнения без переписывания ядра.

При этом capability не может самостоятельно объявлять собственное действие безопасным: окончательное решение принимает Safety & Policy.

3.8. Verification — проверка результата

Verification получает критерии успеха из Goal Model и проверяет их независимыми от простого сообщения об успехе средствами, насколько это возможно.

Например, после создания напоминания проверяет его наличие и время.

Возможные результаты:

VERIFIED_SUCCESS

VERIFIED_FAILURE

PARTIAL_SUCCESS

UNKNOWN

Последнее состояние особенно важно: если система не смогла проверить результат, она не должна утверждать, что задача точно выполнена.

3.9. Model Adapter — адаптер моделей

Единый интерфейс для локальных и облачных моделей.

Agent Core
    ↓
Model Adapter
    ├── Local Model
    ├── Cloud Model A
    └── Cloud Model B

Адаптер стандартизирует запросы, ответы, тайм-ауты и ошибки. Смена модели не должна требовать изменения Agent Core.

Модель предлагает интерпретации и планы, но не получает прямого доступа к системным действиям в обход Execution Engine и Safety & Policy.

3.10. Local State, Experience Store и Audit Log

Эти три компонента выполняют разные задачи.

Local State: текущее состояние задачи, активный шаг, ожидание подтверждения, возможность восстановления после сбоя.

Experience Store: компактные записи об успешных и неудачных стратегиях. На MVP можно начать с простого локального журнала опыта, без сложного самообучения.

Audit Log: значимые действия, проверки, решения о подтверждении и результат. Записи должны минимизировать чувствительные данные и не хранить всё подряд без необходимости.

4. Как модули взаимодействуют при выполнении задачи

STOP — не обычный шаг этого графа. Это отдельный управляющий сигнал, который может поступить почти из любого активного состояния исполнения.

5. STOP AGENT — архитектурное требование

Кнопка STOP должна быть связана непосредственно с управляющим механизмом выполнения, а не просто закрывать экран или скрывать анимацию.

При нажатии:

Блокируется запуск новых действий текущей цепочки.

Посылается сигнал отмены активной операции.

Исполнение прекращается настолько быстро, насколько позволяет используемый механизм.

Фиксируется фактическое состояние: остановлено, частично выполнено или не удалось немедленно прервать операцию.

Пользователь получает понятный статус.

Для защиты от гонок каждый запуск задачи должен иметь собственный идентификатор и токен отмены. Старый план не должен продолжить выполнение после остановки или замены задачи.

Также важно предусмотреть повторное нажатие STOP, потерю процесса Android и операции, которые технически не поддерживают немедленную отмену.

6. Android Runtime и независимость от устройства

Для MVP я предлагаю нативную Android-основу, а не Flutter как обязательный фундамент.

Причина — агенту потребуется глубокая интеграция с разрешениями Android, жизненным циклом приложения, системными API и механизмами выполнения в фоне.

Предварительный технологический вариант:

Kotlin;

Jetpack Compose для интерфейса;

Android API и отдельные адаптеры capabilities;

локальное хранилище состояния;

сменяемый интерфейс к LLM;

изолированный слой голосового ввода и синтеза речи.

Это предварительное предложение, не окончательное технологическое решение.

Нужно отдельно проверить ограничения конкретных версий Android. Например, постоянная работа в фоне, доступ к другим приложениям, автоматизация интерфейса и микрофон имеют разные системные ограничения. Нельзя проектировать агента так, будто он обладает универсальным доступом ко всему устройству.

7. Интерфейс и периферийное присутствие

Interaction Layer остаётся отдельным от Agent Core.

Он получает события состояния и отображает их:

MINIMAL — небольшой аватар;

INTERMEDIATE — раскрытый аватар;

LISTENING — ожидание голоса;

TEXT INPUT — поле ввода;

WORKING — уменьшенный аватар, рабочая область и STOP;

NEED USER — запрос решения;

RESULT — итог задачи.

Напоминания будут отдельным сервисом. В MVP достаточно предусмотреть интерфейс интеграции с ним, а полноценную систему напоминаний можно реализовать позднее.

Приоритет интерфейса:

STOP и безопасность → состояние задачи → запрос пользователя → важные напоминания → декоративная анимация.

8. Что входит в первый вертикальный сценарий

Я бы начинал не с десятков capabilities, а с одного полностью работающего пути.

Этап A — цель и результат

Текстовый ввод → Goal Model → критерии успеха → понятный результат. Пока без опасных системных действий.

Этап B — безопасное выполнение

Одна реальная capability, проверка разрешений, исполнение и верификация.

Этап C — альтернативная стратегия

Первый путь недоступен или не сработал — агент объясняет ситуацию и использует разрешённую альтернативу.

Этап D — остановка

Проверяем, что STOP прерывает цепочку действий и не позволяет старому плану продолжиться.

Этап E — интерфейс и голос

Состояния аватара, голосовой ввод, текстовый fallback, отображение прогресса и результата.

Порядок не означает, что интерфейс создаётся только в конце: его каркас можно подготовить раньше. Но каждый этап должен проверять реальный вертикальный сценарий, а не только отдельные классы.

9. Критерии готовности MVP

Я предлагаю считать MVP готовым, когда выполнены следующие условия:

Пользователь может поставить задачу текстом.
Запрос преобразуется в структурированную цель с критериями успеха.
Агент использует только зарегистрированные capabilities.
Действия проходят проверку безопасности и разрешений.
Результат проверяется, а неизвестный результат не выдаётся за успех.
Неудача может запускать повторное планирование.
STOP прекращает последующие действия и корректно сообщает состояние частично выполненной задачи.
Отсутствие сети или выбранной модели обрабатывается без аварийного падения.
Смена модели не требует изменения Agent Core.
Ключевые переходы состояний покрыты автоматическими тестами.
Пользователь понимает, что агент сделал, что проверил и что осталось незавершённым.
10. Вопросы, которые нужно решить до начала реализации

Архитектурный каркас уже есть, но несколько решений существенно влияют на структуру проекта.

Выбери предпочтительные варианты. Это не окончательные обязательства — они помогут зафиксировать Architecture v0.2.

1. Как агент должен работать без интернета?

Local-first — локальные задачи и локальная модель, когда возможно
Hybrid — локальные функции плюс облако для сложных задач
Online-first — основной расчёт в облаке, локальный режим ограничен

2. С чего начать управление Android-приложениями?

Системные API и официальные интерфейсы приложений
Сразу предусмотреть UI-автоматизацию через Accessibility, с отдельной оценкой рисков и ограничений
Поддерживать оба пути, но предпочитать официальные интерфейсы

3. Какую модель использовать?

Только локальная модель
Только облачная модель
Сменяемые локальные и облачные модели с общим адаптером

4. Как организовать разработку?

Вертикальными этапами: одна задача от ввода до проверенного результата
Сначала создать все архитектурные модули, затем связывать их
Сначала каркас модулей, затем вертикальные сценарии по одному
Зафиксировать выбор

Моя рекомендация — Local-first по архитектуре, официальные Android-интерфейсы как основной путь, сменяемые модели и разработка через вертикальные сценарии.

Это даёт независимое ядро, ограничивает риски и позволяет расширять возможности без переписывания проекта. После согласования этих решений можно зафиксировать Architecture v0.2, определить контракты модулей и только затем создавать проект в Android Studio.
