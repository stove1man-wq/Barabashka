# Glossary — единый словарь контрактов v0.1

**Статус:** Active. Создан 2026-10-12 для устранения расхождений терминов между контрактами (D-006, пункты 1, 2, 4). Расхождения найдены сверкой текстов контрактов. Владелец может править.
**Правило приоритета:** при расхождении терминов между контрактами действует этот документ. Сами контракты не переписаны. В начале шести из них добавлена пометка со ссылкой сюда: оба документа по безопасности и разрешениям, модель разрешений, контракт capability, модель транзакций исполнения и матрица MVP.

## 1. Уровни риска R0–R4

Названия и смысл совпадают во всех документах:

| Уровень | Название | Смысл |
|---|---|---|
| R0 | Informational | чтение, локальные вычисления, без внешних эффектов |
| R1 | Low Impact | обратимые локальные изменения |
| R2 | User-Impacting | изменение пользовательского контента |
| R3 | Sensitive / Consequential | связь с третьими лицами, отправка данных наружу, значимые последствия |
| R4 | Highly Sensitive | финансы, критические или необратимые действия, настройки безопасности |

**Риск конкретной capability** задаёт только таблица `independent_android_ai_agent_capability_matrix_mvp_v0.1.md` (CAP-001…CAP-024). Примеры в других контрактах носят иллюстративный характер и ничего не определяют. Эффективный риск конкретного вызова может быть выше базового (контекст данных, цель).

Расхождения примеров, которые были найдены и сняты этим правилом:

| Capability | Где что сказано | Действует |
|---|---|---|
| `message.send` | R3 в матрице MVP и коротком контракте безопасности; R2 в подробном контракте безопасности | **R3** |
| `reminder.create` | R2 в матрице MVP; «локальное напоминание» как R1 в подробном контракте | **R2** (по матрице) |
| `web.search` | R1 в матрице MVP; R0 в коротком контракте | **R1** (запрос покидает устройство) |

## 2. Состояния разрешения (Permission State)

Каноническое множество — объединение трёх найденных списков:

| Состояние | Смысл |
|---|---|
| `UNKNOWN` | состояние не определено |
| `NOT_REQUIRED` | разрешение для действия не нужно |
| `NOT_GRANTED` | требуется, но ещё не выдано (прежнее `NOT_REQUESTED`) |
| `REQUESTABLE` | не выдано, но можно запросить у пользователя |
| `GRANTED` | выдано |
| `TEMPORARILY_GRANTED` | выдано на сессию или один раз |
| `DENIED` | отказано, запрос возможен снова |
| `PERMANENTLY_DENIED` | отказано без повторного запроса из приложения |
| `REVOKED` | было выдано, затем отозвано пользователем или системой |
| `RESTRICTED` | ограничено политикой или системой |
| `TEMPORARILY_UNAVAILABLE` | сейчас недоступно по внешней причине |

Источники: `safety_permission_contract` (подробный) — основа; `permission_security_model` добавил `TEMPORARILY_GRANTED`, `REVOKED`, `NOT_REQUESTED`.

## 3. Решение Safety Policy (Safety Decision)

Каноническое множество — из подробного контракта безопасности:

| Значение | Смысл | Прежние синонимы |
|---|---|---|
| `ALLOW` | выполнять | — |
| `ALLOW_WITH_CONFIRMATION` | выполнять после подтверждения пользователя | `REQUIRE_CONFIRMATION`, `CONFIRM` |
| `WAIT_FOR_PERMISSION` | ждать выдачи Android-разрешения | `PERMISSION` (краткая запись в разделе 31 подробного контракта) |
| `WAIT_FOR_USER` | ждать иного ответа пользователя | — |
| `BLOCK` | запретить | `DENY` |

Правило «deny by default» из модели разрешений означает: при недостатке данных решение — `BLOCK`.

## 4. Подтверждение: два разных слоя

В документах было два набора под одним названием. Это разные понятия.

**Политика, объявленная capability** (`capability_contract`): `NEVER_REQUIRED`, `CONTEXTUAL`, `ALWAYS_REQUIRED`, `POLICY_BLOCKED`.
**Уровень, вычисленный Safety Policy для вызова** (`safety_permission_contract`): `NONE`, `OPTIONAL`, `REQUIRED`, `REQUIRED_EVERY_TIME`.

Соответствие:

| Объявлено capability | Вычисленный уровень |
|---|---|
| `NEVER_REQUIRED` | `NONE` (может быть повышено при росте эффективного риска) |
| `CONTEXTUAL` | `NONE`, `OPTIONAL` или `REQUIRED` по контексту |
| `ALWAYS_REQUIRED` | `REQUIRED` или `REQUIRED_EVERY_TIME` |
| `POLICY_BLOCKED` | решение `BLOCK` |

## 5. Три разных вида «состояния»

Слово «состояние» использовалось для трёх разных вещей. Не смешивать:

1. **Доступность capability** (`architecture_decisions`, `capability_contract`): `AVAILABLE`, `UNAVAILABLE`, `BLOCKED`, `REQUIRES_PERMISSION`, `REQUIRES_USER`, `TEMPORARILY_UNAVAILABLE`, `UNKNOWN`.
2. **Состояние транзакции исполнения** (`execution_transaction_model`): `CREATED`, `VALIDATING`, `READY`, `EXECUTING`, `OBSERVING`, `VERIFYING`, затем `COMMITTED`, `FAILED`, `ABORTED`, `RECOVERY_REQUIRED` (минимальная машина состояний). Состояния `REQUIRES_PERMISSION` у транзакции нет. Фраза «транзакция переходит в стейт `REQUIRES_PERMISSION`» в коротком контракте безопасности означает: решение Safety Policy `WAIT_FOR_PERMISSION` и приостановку исполнения.
3. **Состояние разрешения** — раздел 2.

## 6. Платформенные термины (D-005)

В контрактах упоминаются Kotlin, Compose, `ActivityCompat.requestPermissions`, Ktor, Filament. Платформа проекта — Unity (C#). Нормативны обязанности и интерфейсы, а не названия API. Запрос разрешений выполняется через официальный механизм Android, в Unity — через его API или нативный плагин (точный вызов проверять по документации версии Unity).
