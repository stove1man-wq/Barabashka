# Next Steps

**Обновлено:** 2026-10-12
**Платформа:** Unity 6000.6.5f1, C# (D-005, Accepted).
**Правило:** работаем строго по порядку. Следующий этап не начинается, пока не выполнены критерии текущего. Новые архитектурные документы не пишем, пока не проверен Slice 1 (D-006, пункт 3, предложение).

## M0 — Базовая линия и порядок в репозитории (сейчас)

Прототип запускается в эмуляторе и получает ответ Ollama (сообщение владельца, 2026-10-12). Теперь его нужно зафиксировать, чтобы от него можно было отталкиваться.

1. Записать в `DEVELOPMENT_LOG.md`, что именно исправило «зависание» (настройка «Allow downloads over HTTP», пересборка, другое) и версию APK.
2. Принять или изменить D-009 (расположение Unity-проекта): рекомендация — папка `unity/` в этом репозитории.
3. Перенести в репозиторий только `Assets/`, `Packages/`, `ProjectSettings/` (без `Library/`, `Temp/`, `Logs/`, `Builds/`, `UserSettings/`). Включить Asset Serialization = Force Text.
4. Сделать первый коммит проекта и убедиться, что чистая копия репозитория открывается в Unity и собирается.
5. Настроить VS Code по `docs/agent/SETUP_VSCODE.md` и проверить, что Cline и Continue видят правила.
6. Добиться, чтобы исполнитель создаёт и правит файлы (диагностика — `docs/agent/SETUP_VSCODE.md` §1а). Без этого цикл «карточка → исполнение» не работает.

**Критерии завершения:**
- Unity-проект под git в GitHub, `.gitignore` работает (в коммите нет `Library/` и `.apk`);
- свежий клон открывается в Unity 6000.6.5f1 и собирается в APK;
- новый чат с Cline по фразе из SETUP_VSCODE.md верно пересказывает состояние проекта и следующий шаг;
- Cline по просьбе создаёт файл `test.txt` и правит существующий (результат и использованная модель записаны в журнале);
- версия сборки видна на экране приложения.

## M0.1 — Укрепление прототипа (параллельно или сразу после M0)

1. Таймаут запроса, вывод статуса и текста ошибки на экран, кнопка отмены.
2. Адрес и модель вынесены из UI-кода в интерфейс клиента модели (D-007), Ollama — одна реализация.
3. Проверить, к чему привязана Ollama: loopback или `0.0.0.0` (D-008). Закрыть последний пункт в `android_integration_architecture_v0.1.md` (раздел 6).

**Критерий:** сеть недоступна или модель не отвечает — приложение показывает понятную ошибку и не зависает.

## M0.2 — Связка агента с Unity (уровень L1, D-011)

Подробности: `docs/agent/UNITY_BRIDGE.md`. Делается после M0, перед M2.

1. Расширения VS Code и пакет `com.unity.ide.visualstudio` (≥ 2.0.20) по руководству Unity для вашей версии; *Regenerate project files*.
2. Выделить Core в `asmdef` без `UnityEngine`; добавить Unity Test Framework (по согласованию, `AGENTS.md` §5) и один EditMode-тест.
3. Записать в `PROJECT_STATUS.md` точную команду запуска тестов в batchmode, которая реально сработала.

**Критерии:** (а) намеренная ошибка в `.cs` подчёркнута в VS Code; (б) агент по просьбе находит в `Editor.log` ошибку компиляции и называет файл и строку; (в) агент запускает один EditMode-тест из терминала и показывает результат. L2 (Unity MCP) в этот этап не входит.

## M1 — Spike: Unity и системные возможности Android

Решение о платформе принято (Unity). Неизвестно другое: насколько удобно из Unity вызывать системные возможности Android. Проверить на одном настоящем сценарии `calendar.create_event` + чтение события обратно.

1. Вызов календаря из Unity: нативный плагин в `Assets/Plugins/Android` (Java или Kotlin) и вызов из C#. Время и число обязательных мостов записать.
2. Запрос разрешения календаря во время выполнения и обработка отказа.
3. Проверить на эмуляторе, затем на устройстве, если оно есть.
4. Отдельно оценить, без реализации: foreground-сервис, оверлей `SYSTEM_ALERT_WINDOW`, роль ассистента совместно с Unity-активностью. Записать, возможно ли это и какой запасной путь (тонкая нативная оболочка, хостящая Unity как библиотеку).

**Критерии:** событие создано и прочитано обратно из C#; отказ в разрешении обработан без падения; оценка оверлея и сервиса записана в `DECISIONS.md` (D-005, раздел рисков).

## M2 — Slice 1: первый вертикальный срез

Цель: один настоящий путь Goal → Plan → Safety → Execute → Verify → Result.

**Входит:**
- текстовый ввод цели («создай событие завтра в 18:00 …»);
- цель как структурированный объект с критериями успеха (модель через адаптер возвращает JSON, наш код его валидирует);
- одна capability: `calendar.create_event` (R2 по матрице MVP, нужно подтверждение пользователя; решение Safety Policy `ALLOW_WITH_CONFIRMATION`);
- две стратегии: прямая запись (через Android bridge) и запасная через системный intent. Выбор по статическому приоритету, без модели скоринга;
- проверка результата: прочитать событие обратно и сравнить с целью;
- STOP с токеном отмены на запуск; повторный STOP безопасен;
- аудит-лог в упрощённом виде (что запросили, что решили, что выполнили, что проверили);
- терминология по `docs/architecture/GLOSSARY.md`.

**Не входит:** аватар, голос, память, обучение на опыте, центральный сервер знаний, остальные capabilities, UI-автоматизация.

**Критерии (из 11 критериев MVP в `777.txt`):**
1. Цель из текста превращается в структуру с критериями успеха.
2. Используются только зарегистрированные capabilities.
3. Действие проходит проверку безопасности и запрашивает подтверждение.
4. Неподтверждённый результат не объявляется успехом.
5. Сбой первой стратегии запускает вторую.
6. STOP прекращает последующие шаги и честно сообщает частично выполненное.
7. Отсутствие модели или сети не роняет приложение.
8. Замена модели (вторая заглушка-реализация адаптера) не требует правки ядра.
9. Переходы состояний покрыты автоматическими тестами (Core — чистый C#, тесты без Unity).

Каждый критерий проверяется тестом или записанным ручным сценарием.

## M3 — Укрепление адаптера модели

- Вторая реализация адаптера (заглушка или облачный провайдер) для доказательства независимости от модели.
- Структурированный вывод и валидация. Проверить по документации Ollama для вашей версии.
- Недоступность, таймауты, повторы.

## M4 — Android-слой

- Foreground-сервис, постоянный STOP, разрешения как отдельная подсистема (по итогам M1).
- Подтверждения пользователя в UI. Расширение аудита.

## M5 — Остальные capabilities

По одной, в порядке из матрицы MVP (P0: `device.get_state`, `calendar.search_events`, `calendar.update_event`). Каждая — отдельный срез с критериями приёмки.

## M6 — Local-first на самом деле

Исследование запуска модели на устройстве: что доступно на целевом телефоне, какой размер модели реалистичен, ограничения по памяти и батарее. Результат — запись в `DECISIONS.md`, а не сразу реализация.

## M7 — Аватар и присутствие

3D-аватар в Unity (glTF/GLB, Animator), режимы MINIMAL/WORKING, присутствие поверх других приложений (зависит от результатов M1). Только после M2 и M4.

## Что намеренно отложено

Маркетплейс, самообучение (RL), центральная сеть знаний, универсальная UI-автоматизация, мульти-агентность. Архитектура должна оставлять место для них, но работа над ними не начинается.
