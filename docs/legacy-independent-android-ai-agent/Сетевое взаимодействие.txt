Сервер:

Не выполняет запросы пользователей
Не хранит и не связывает персональные данные с окружением
Собирает и актуализирует информацию об окружающей среде
По запросу агента отдаёт метки (labels / флаги / актуальные правила)

Примеры меток:

Какие сетевые магазины/сервисы сейчас доступны или закрыты
Изменения в законах, которые запрещают или ограничивают определённые действия/алгоритмы
Актуальные способы доступа к нужным сервисам
Возможно — регистрация и выдача API-ключей / токенов для работы с внешними сервисами
Обновления правил и политик, общих для всех агентов

Агент:

Хранит персональный контекст и память о пользователе
Принимает решение, используя:
Локальные правила
Локальную память
Метки, полученные от сервера

Выполняет действия от имени пользователя
1. Протокол обмена метками между агентом и сервером
Цель протокола — сделать обмен максимально обезличенным, простым, надёжным и удобным для агента, при этом минимизировать любые риски по 152-ФЗ.
Основные принципы протокола

Агент никогда не отправляет на сервер идентификаторы пользователя, device_id, историю диалогов или персональный контекст.
Запрос строится только вокруг необходимости («какие метки мне нужны»).
Сервер отвечает только данными об окружении и правилами.
Все запросы по возможности должны быть кэшируемыми и не персонализированными.

Рекомендуемая модель запроса (от агента к серверу)
Агент отправляет примерно такой запрос:
JSON{
  "protocol_version": "1.0",
  "request_id": "uuid",              // только для отслеживания ответа, не привязан к пользователю
  "agent_version": "x.y.z",
  "requested_marks": [
    {
      "category": "services.availability",
      "filters": {
        "region": "RU-MOW",
        "service_type": ["food_delivery", "pharmacy"]
      }
    },
    {
      "category": "legal.restrictions",
      "filters": {
        "domain": ["purchases", "data_transfer"]
      }
    },
    {
      "category": "api.access",
      "filters": {
        "service": ["some_service_name"]
      }
    }
  ],
  "locale": "ru-RU",
  "timestamp": "2026-10-09T04:00:00Z"
}
Важные моменты:

Нет user_id, device_id, session_id.
request_id нужен только для сопоставления запроса и ответа, после использования можно забывать.
Фильтры — только обезличенные (регион, тип сервиса, домен законов и т.д.).

Дополнительные правила протокола

Кэширование
Агент обязан кэшировать полученные метки согласно ttl. Не должен дёргать сервер по каждому действию.
Приоритет меток
Если есть конфликт правил, приоритет отдаётся меткам с более высокой severity / priority.
Отказоустойчивость
Если сервер недоступен — агент работает на последних известных метках + локальных правилах, и честно сообщает об этом при необходимости.
Минимизация данных в запросе
Агент запрашивает только те категории меток, которые реально нужны для текущей задачи.
Версионирование
Обязательно поле protocol_version, чтобы можно было эволюционировать протокол без поломки старых агентов.
Безопасность канала
Обмен только через защищённый канал (TLS). Желательно предусмотреть возможность подписи ответов сервера, чтобы агент мог проверять подлинность меток

бновлённый принцип минимизации запросов:

Агент делает плановый запрос меток не чаще одного раза в сутки.
Дополнительный внеплановый запрос — только если сервер прислал сигнал о наличии критических обновлений.
В остальное время агент работает на закэшированных метках.
